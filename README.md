# Лаб 03 — Чанарын шинжийн сценариуд

Энэ баримт нь [server.js](server.js) API-д зориулсан **performance**, **reliability**,
**availability** гэсэн гурван сценариог Лекц 3-ын 6 хэсэгтэй форматаар тодорхойлно.

Сценарийн бүх хэмжүүр нь таамаг биш — доорх "Хэмжилтийн орчин" хэсэгт заасан нөхцөлд гүйцэтгэсэн
k6 туршилтын **бодит үр дүн** дээр тулгуурласан.

---

## Хэмжилтийн орчин (baseline)

| Зүйл | Утга |
|---|---|
| Тоног төхөөрөмж | Apple M4, 10 цөм |
| Ажиллах орчин | Node.js v20.20.2, Express 5.2.1, нэг процесс |
| Ачаалал үүсгэгч | k6 v2.2.0, `constant-arrival-rate` executor |
| Сүлжээ | localhost (сүлжээний саатал ≈ 0) |

> **Тайлбар.** `constant-vus` биш `constant-arrival-rate` ашигласан. Учир нь хаалттай
> давталттай (closed-loop) 50 VU нь серверийг ханатал нь дарж 23,999 хүсэлт/с өгсөн —
> энэ бол хүчин чадлын дээд хязгаар (saturation) болохоос "хэвийн ачаалал" биш.
> Хэвийн ачааллыг **хүсэлт/с**-ээр тогтоож хэмжсэн.

## 1. Performance сценарио — `/cart/add` хариу хугацаа

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Хэвийн худалдааны ачаалал үед хэрэглэгч сагсанд бараа нэмэх үйлдлийн хариу хугацаа хүлээн зөвшөөрөгдөх хэмжээнд байх. |
| **Системийн төлөв** | Хэвийн ажиллагаа. Нэг Node процесс, in-memory төлөв, degraded горимд ороогүй, санах ой хэвийн. |
| **Орчны төлөв** | Холимог ачаалал 60 секундын турш: `/cart/add` **500 хүсэлт/с**, `/report` 50 хүсэлт/с, `/pay` 100 хүсэлт/с — нийт **≈650 хүсэлт/с**. Ачаалал тогтмол (arrival rate), огцом өсөлтгүй. |
| **Гадаад өдөөлт** | Хэвийн хэрэглэгч бараагаа сагсанд нэмнэ: `POST /cart/add`. |
| **Шаардлагатай хариу** | Систем `200 OK` статус ба `{ok, items}` JSON-г зөв буцаана. Хүсэлт алдагдахгүй, timeout болохгүй, удаан `/report` хүсэлтүүд `/cart/add`-ийн замыг блоклохгүй. |
| **Хэмжүүр** | Ижил орчинд хэмжихэд: **p95 ≤ 5 мс**, **p99 ≤ 15 мс**, алдааны хувь **< 0.1%**, хаягдсан хүсэлт (dropped iterations) = **0**. |

**Хэмжсэн үр дүн** (30 с холимог ачаалал, `/cart/add`-ийн **15,001** хүсэлт):
p95 = **0.66 мс**, p99 = **1.22 мс**, максимум 59.3 мс, алдаа **0%**, хаягдсан хүсэлт 0.
Жишиг болгоход зэрэг ажиллаж байсан `/report` нь p95 = 392 мс (зориудын 200–400 мс саатал).

**Дүгнэлт:** ✅ Хангаж байна, зорилтоос ~7 дахин нөөцтэй. Зорилтыг baseline-аас
санаатай өндөр (5 мс) тавьсан нь ирээдүйд код өөрчлөгдөхөд **регресс илрүүлэх хамгаалалт**
болно. Удаан `/report` зэрэг ажиллаж байхад `/cart/add` удаашраагүй нь `setTimeout`
event loop-ийг блоклодоггүйг батлав.

## 2. Reliability сценарио — `/pay` эвдрэлийн давтамж

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Төлбөрийн endpoint хэвийн ажиллагааны үед хэр олон удаа бүтэлгүйтэж байгааг хэмжиж, зөвшөөрөгдөх хязгаарт байлгах. |
| **Системийн төлөв** | Хэвийн ажиллагаа. Төлбөрийн gateway-тэй холболт тогтсон, сүлжээний тасалдалгүй. |
| **Орчны төлөв** | Хэвийн ачаалал: `/pay` **100 хүсэлт/с**, 60 секунд, нийт **≥6,000 хүсэлт**. Дээжийн хэмжээг статистик итгэлцэл хангахуйцаар сонгосон. |
| **Гадаад өдөөлт** | Хэвийн хэрэглэгч "Төлөх" товч дарна: `POST /pay`. Энэ нь **эвдрэл биш, хэвийн үйлдэл**. |
| **Шаардлагатай хариу** | Амжилттай бол `{paid: true}` буцаана. Бүтэлгүйтвэл тодорхой `5xx` алдаа буцааж, **давхар төлбөр үүсгэхгүй** (idempotency түлхүүрээр хамгаална), клиент дахин оролдох (retry) боломжтой байна. Алдаа чимээгүй залгигдахгүй. |
| **Хэмжүүр** | **POFOD ≤ 0.005** (1,000 хүсэлтэд ≤5 эвдрэл), 95% итгэлцлийн интервалаар баталгаажуулна. Нэмэлт: `/pay`-ийн p95 ≤ 5 мс. |

**Хэмжсэн үр дүн** (60 с ачаалал, 6,000 төлбөрийн хүсэлт):
POFOD = **0.0485** (291 эвдрэл), 95% итгэлцлийн интервал = **[0.043, 0.054]**.
Бие даасан давтан хэмжилт (30 с, 3,001 хүсэлт): POFOD = 0.0439 — хоорондоо нийцэж байна.
Эвдрэл нь хурдан илэрдэг: `/pay`-ийн p95 = 0.83 мс, өөрөөр хэлбэл timeout биш шууд 500.

**Дүгнэлт:** ❌ **Хангахгүй.** Хэмжсэн POFOD нь шаардлагаас **~10 дахин их**, итгэлцлийн
интервал нь 0.005 зорилтыг огт давхцахгүй — өөрөөр хэлбэл энэ бол санамсаргүй хэлбэлзэл
биш, системийн шинж. Шалтгаан нь [server.js:27](server.js#L27) дээрх 5% алдааны
логик бөгөөд retry ч, idempotency ч хэрэгжээгүй байна.

## 3. Availability сценарио — гэнэтийн уналт ба сэргэлт

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Серверийн процесс гэнэт унаад дахин асах үед систем хэр хурдан сэргэж, хэрэглэгчид ямар хэмжээний тасалдал мэдрэгдэхийг тодорхойлох. |
| **Системийн төлөв** | Уналтаас өмнө хэвийн ажиллагаатай, хэрэглэгчдэд идэвхтэй үйлчилж байсан. |
| **Орчны төлөв** | Ажлын цагийн тогтмол ачаалал **200 хүсэлт/с**. Дэд бүтэц (хост, сүлжээ) хэвийн — зөвхөн процесс унана. |
| **Гадаад өдөөлт** | **ЭВДРЭЛ (crash):** процесс гэнэт зогсох — `SIGKILL`, барьцаагүй exception, эсвэл санах ойн хэтрэлт (OOM). Урьдчилсан сануулгагүй. |
| **Шаардлагатай хариу** | Процессыг хянагч (supervisor: systemd / pm2 / Docker `restart: always`) уналтыг илрүүлж **автоматаар дахин асаана**. Сэргэх хүртэлх хүсэлтүүд удаан хүлээлгэлгүй **шуурхай бүтэлгүйтэж** (fail-fast), клиент дахин оролдоно. Дахин асахад өгөгдөл гэмтэхгүй, гараар оролцох шаардлагагүй. |
| **Хэмжүүр** | • **Бэлэн байдал ≥ 99.9% сард** (сард ≤43.2 минут тасалдал)<br>• **Сэргэх хугацаа (MTTR): p95 ≤ 5 с, p99 ≤ 15 с**<br>• Нэг уналтад алдагдах хүсэлт **≤ 1,000** (200 хүсэлт/с × 5 с) |

**Хэмжсэн үр дүн:**

| Үзүүлэлт | Утга |
|---|---|
| Процесс асаж бэлэн болох хугацаа | **72–90 мс** (5 удаагийн хэмжилт) |
| 3.1 с тасалдлын симуляцид алдагдсан хүсэлт | **620 / 6,001** |
| Тухайн 30 с цонхны бэлэн байдал | **89.66%** |

**Дүгнэлт:** ❌ **Хангахгүй — гэхдээ шалтгаан нь кодонд биш, дэд бүтцэд байна.**
Процесс дахин асахад ердөө ~80 мс зарцуулдаг тул 5 секундын MTTR зорилт техникийн
хувьд бүрэн боломжтой. Гэвч одоо ямар ч supervisor тохируулаагүй учир уналтыг
**хүн илрүүлэх хүртэл** систем унтарсан хэвээр байна — MTTR нь хэдэн минут, цаг ч
байж болно. Тиймээс бодит MTTR-ийг хэмжих боломжгүй, бэлэн байдлын зорилт хангагдахгүй.

> Хэрэв supervisor нэмж MTTR-ийг 5 с болговол: долоо хоногт 1 удаа унана гэж тооцоход
> сард ≈4.3 уналт × 5 с = **21.5 с тасалдал = 99.999%** — зорилтыг тайван давна.
> Өөрөөр хэлбэл дутуу зүйл бол **илрүүлэлт**, гүйцэтгэл биш.

## Нэгдсэн дүгнэлт

| Сценарио | Зорилт | Хэмжсэн | Үр дүн |
|---|---|---|---|
| Performance `/cart/add` | p95 ≤ 5 мс | p95 = 0.66 мс | ✅ |
| Reliability `/pay` | POFOD ≤ 0.005 | POFOD = 0.0485 | ❌ 10 дахин зөрүү |
| Availability (crash) | ≥99.9%, MTTR p95 ≤ 5 с | автомат сэргэлт байхгүй | ❌ |

Гурван сценариогоос хоёр нь унасан нь **сценарийн үнэ цэнийг** харуулж байна:
"систем хурдан байна" гэсэн ерөнхий мэдэгдлээр илрэхгүй хоёр тодорхой цоорхойг
тоогоор баримтжуулж өглөө.

## "Сайн сценариогийн 5 шинж"-ээр өөрийгөө шалгасан нь

| Шинж | Хэрхэн хангасан |
|---|---|
| **Итгэмжтэй** | Гурван сценарийн өдөөлт бүр бодит нөхцөл — сагс нэмэх, төлбөр хийх, процесс унах. Бүх хэмжүүр таамаг биш, k6-аар бодитоор хэмжигдсэн, давтагдах боломжтой. |
| **Үнэ цэнэтэй** | Хоёр сценарио бодит цоорхой илрүүлсэн (POFOD 10 дахин их; автомат сэргэлт байхгүй). Аль аль нь хөгжүүлэлтийн тодорхой ажил үүсгэж байна. |
| **Тодорхой** | Өдөөлт (юу тохиолдов) ба шаардлагатай хариу (систем юу хийх ёстой) хоёрыг тусад нь бичсэн. Ачааллыг "их" гэхгүй, **хүсэлт/с**-ээр заасан. |
| **Нарийн** | Бүх хэмжүүр тоон утгатай ба магадлалын хуваарилалттай (p95/p99, POFOD, %). Хэмжих нөхцөлийг (тоног төхөөрөмж, ачаалал, дээжийн хэмжээ) тодорхойлсон тул үр дүн давтагдана. |
| **Ойлгомжтой** | 6 хэсэгтэй нэгдсэн хүснэгт, хэмжсэн үр дүн ба дүгнэлт тус бүрдээ. Техникийн бус уншигч ч "юу болов / юу байх ёстой / хангасан уу" гэдгийг уншиж чадна. |

## Хэмжилтийг давтах

**1, 2-р сценарио** (холимог ачаалал, latency + POFOD):

```bash
node server.js &                    # API-г асаана (http://localhost:3000)
k6 run mixed.js
```

**3-р сценарио** (уналт + сэргэлт). `crash.js` дангаараа серверийг унагаахгүй тул
уналтыг зэрэгцээ өдөөнө — доорх тушаал t=10с үед процессыг `SIGKILL`-ээр унагааж,
3 секундын дараа supervisor мэт дахин асаана:

```bash
node server.js &
( sleep 10; pkill -9 -f "node server.js"; \
  sleep 3;  node server.js & ) &
k6 run crash.js
```

`availability` хэмжүүр нь тухайн 30 секундын цонхны бэлэн байдлыг харуулна.
Сэргэх хугацааг тусад нь хэмжихдээ процессыг унагаагаад эхний амжилттай
хариу хүртэлх хугацааг тоолно (хэмжсэн утга: 72–90 мс).

**Алхам 3-ын SLO хэмжилт** (20 VU / 1 мин — latency ба error rate босго шалгах):

```bash
node server.js &
k6 run slo20.js
```

**Алхам 3-ын error budget хэмжилт** (2 мин цонх, дунд нь 10 с зогсолт):

```bash
node server.js &
( sleep 40; pkill -9 -f "node server.js"; \
  sleep 10; node server.js & ) &
k6 run avail.js
```

`avail.js` нь `availability` хэмжүүрийг **хүсэлтээр** тооцдог тул 90%-ийн threshold
унана — энэ нь алдаа биш, Алхам 5-д задлах цаг/хүсэлтийн зөрүүг харуулж буй хэрэг.
